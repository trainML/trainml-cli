# Plan: ride out CF-tunnel-recycling 404 windows in `upload()` and `download()`

## Problem
During Cloudflare tunnel recycling, the hostname is briefly unmapped and the CF
edge answers **404** for every request to it. On `trainml job connect`:
- `ping_endpoint` already absorbs 404s (9 attempts, exp. backoff) ✓
- `/info` 404 is swallowed (debug log, TAR-mode fallback) ✓
- **`/download` 404 is fatal on the first attempt** — raw
  `aiohttp ClientResponseError` propagates (no retry, no friendly message) →
  CLI shows `Error: 404, message='Not Found', url=.../download`
- Same gap on the **upload** side: 404 on the chunk PUT →
  `upload_chunk` raises `TrainMLConnectionError("Chunk ... failed with status 404")`
  → fatal, no retry.

The pod is up ("Ready for transfer"); the failure is purely the edge window.

## Decisions (confirmed with user)
- Retry 404s at a **fixed 15 s cadence, up to 9 retries** (~2.25 min) — on both
  the **upload** and **download** paths.
- A *genuine* pod 404 (file missing) now fails after the full 9×15 s wait.

## Changes — `trainml/utils/transfer.py`

### 1. New constants (next to the DNS constants, ~:43-57)
```python
# While a Cloudflare tunnel is recycling, the hostname can be unmapped and the
# edge returns 404 for a while. Retry requests at this fixed cadence to ride
# out the window.
NOT_FOUND_RETRY_DELAY = 15  # seconds to wait between 404 retries
NOT_FOUND_MAX_RETRIES = 9
```

### 2. `upload_chunk` (~:836-856)
Add a 404 branch alongside 409 (merge into one `elif`, identical behavior):
`elif response.status in RETRY_STATUSES or response.status in (404, 409):` →
raise `ClientResponseError` (so the caller can tell 404 apart from hard
errors). The `else` → `TrainMLConnectionError("Chunk ... failed ...")` branch
stays for other statuses.

### 3. `upload()` chunk loop (~:955-1036)
- Init `not_found_retries = 0` before the `while True:` chunk loop.
- In the chunk-success path (where `offset = end + 1` is set), reset
  `not_found_retries = 0` (a completed chunk means the tunnel is healthy again;
  each recycle window gets its own full budget).
- In `except ClientResponseError as e:`, **before** the existing
  `if e.status not in RETRY_STATUSES and e.status != 409: raise` check, add:
  ```python
  if e.status == 404:
      if not_found_retries >= NOT_FOUND_MAX_RETRIES:
          raise TrainMLConnectionError(
              f"Upload endpoint returned 404 after "
              f"{NOT_FOUND_MAX_RETRIES} retries; the endpoint may not be ready "
              f"yet (tunnel recycling). Last error: {e.message}"
          ) from e
      not_found_retries += 1
      logging.warning(
          "Upload endpoint returned 404; retry %s/%s in %ss (tunnel may be recycling)",
          not_found_retries, NOT_FOUND_MAX_RETRIES, NOT_FOUND_RETRY_DELAY,
      )
      await asyncio.sleep(NOT_FOUND_RETRY_DELAY)
      continue  # re-upload the same buffered chunk at the same offset
  ```
  Safe: while the hostname is unmapped the chunk never reaches the pod, so
  retrying the same offset is idempotent; if it *did* slip through, the
  existing offset-desync recovery still applies.

### 4. `download()` (~:1196-1228)
Replace the current single try/except around `retry_request(_download)` with a
bounded 404 wait loop; keep the NXDOMAIN→c-ares one-shot retry semantics intact
by moving it into a helper:
```python
async def _download_once():
    try:
        return await retry_request(_download)
    except ClientConnectorError as e:
        if _is_dns_name_not_known(e):
            await state.open(RESOLVER_MODE_CARES)
            return await retry_request(_download)
        raise

not_found_retries = 0
while True:
    try:
        response = await _download_once()
        break
    except ClientResponseError as e:
        if e.status != 404:
            raise
        if not_found_retries >= NOT_FOUND_MAX_RETRIES:
            raise TrainMLConnectionError(
                f"Download endpoint returned 404 after "
                f"{NOT_FOUND_MAX_RETRIES} retries; the endpoint may not be ready "
                f"yet (tunnel recycling). Last error: {e.message}"
            ) from e
        not_found_retries += 1
        logging.warning(
            "Download endpoint returned 404; retry %s/%s in %ss (tunnel may be recycling)",
            not_found_retries, NOT_FOUND_MAX_RETRIES, NOT_FOUND_RETRY_DELAY,
        )
        await asyncio.sleep(NOT_FOUND_RETRY_DELAY)
```
- Non-404 `ClientResponseError`s still propagate raw (existing tests rely on
  that, e.g. `test_download_non_404_error_status`).
- The existing `use_archive` decision + Content-Type rescue (~:1230) is
  untouched: an `/info` 404 during the window still falls back to TAR mode and
  the Content-Type check corrects it.
- No changes to `ping_endpoint`, `jobs.py`, or the CLI.

## Changes — `tests/unit/utils/test_transfer_unit.py`
All new tests patch `asyncio.sleep` (AsyncMock) so they run instantly; 404s go
through the **real** `retry_request` (call-through mock), matching the
finalize-retry test pattern.

   `ClientResponseError` escapes `download()`. New behavior: 9 retried 404s then
   `TrainMLConnectionError`. Patch `asyncio.sleep`; assert
   `raises(ConnectionError, match="404")` and `mock_sleep` awaited 9 times.
2. **New** `test_download_404_retries_then_success`: GET → 404, 404, then
   200-TAR stream; assert no exception, 3 GETs to `/download`, sleep awaited 2×
   (modeled on `test_download_finalize_retries_transient_error`, incl. the
   tar-subprocess mock).
3. **New** `test_upload_chunk_not_found_raises_cse` (direct `upload_chunk`):
   PUT mock → 404 response, call-through `retry_request` →
   `raises(ClientResponseError)` with `status == 404`.
4. **New** `test_upload_404_retries_then_success`: subprocess mock
   (`stdout.read` → `[b"data", b""]`), **unpatched** `upload_chunk`,
   `session.put` → 404 then 200 `{"expected_offset": 4}`; assert upload
   completes, `put` called 2×, sleep awaited 1×.
5. **New** `test_upload_404_exhaustion_fails`: `session.put` → always 404;
   assert `raises(ConnectionError, match="404")`, sleep awaited 9×, `put`
   called 10×.

Check `test_upload_chunk_error_status_direct` (:1102) uses a non-404 status
